# 压力管道服务 · 本地开发环境复现指南

本指南把「依赖准备 → 容器构建 → 样例数据初始化 → 结果核验」固定成一套照着做就能复现的步骤。
照着执行后，换一台机器、或在容器里，跑出来的都是同一份结果。

> 适用范围：本仓库（特种设备点检运维平台）整体；第 5 节的导出条数核验以压力管道模块为准。

## 0. 版本基线（所有版本都有记录、可复现）

| 组成 | 本地要求 | 容器固定版本 | 版本依据 |
| --- | --- | --- | --- |
| Python | 3.11.x（≥ 3.11，建议 3.11.2+） | `python:3.11.16-slim-bookworm` | `backend/Dockerfile` |
| Node.js | 20.x（开发机实测 20.20.2） | `node:20.20.2-alpine3.22` | `frontend/Dockerfile` |
| 后端依赖 | 以 `backend/requirements.lock` 为准 | 同一份 lock | 锁文件（`==` 精确版本） |
| 前端依赖 | 以 `frontend/package-lock.json` 为准 | 同一份 lock | `npm ci` 严格按锁安装 |
| 数据库 | 无（后端为纯内存数据仓库，见 `app/store.py`） | 无 | 不需要数据库 |
| 缓存 | 无 | 无 | 不需要缓存 |

后端直接依赖声明在 `backend/requirements.txt`（`fastapi`/`uvicorn`/`pydantic`），
**实际安装版本一律以 `requirements.lock` 为准**；前端同理，`package.json` 只声明范围，
实际版本以 `package-lock.json` 为准。

> 说明：当前后端是内存实现（进程启动即装载 `app/seed.py` 的样例数据），
> 所以不存在「数据库/缓存版本没人记录」的问题——这两项依赖为零。
> 将来接入真实数据库/缓存时，版本同样要写进这张表并在 `docker-compose.yml` 固定镜像 tag。

## 1. 第 0 步：环境体检（先看缺什么）

在仓库根目录：

```bash
make check-env                # 只查本地直跑所需条件
# 或：./scripts/preflight.sh
make check-env ARGS=--with-docker   # 连容器条件（docker / compose v2 / 守护进程）一起查
```

体检逐项输出 `[OK]` / `[缺失]`，**哪一项没过会直接写明缺的是什么、怎么补**，例如：

- `python3` 缺失或低于 3.11 → 安装 Python 3.11+（Debian/Ubuntu：`python3`、`python3-venv`；
  没有 root 也没关系，第 2 步的脚本会用 `venv --without-pip` + `get-pip.py` 引导）。
- `npm`/Node 缺失或主版本不是 20 → 安装 Node 20.x（与容器 20.20.2 对齐）。
- 访问不到 `pypi.org` / `registry.npmjs.org` → 配置网络或公司内网镜像源。
- 容器方式缺 `docker compose` v2 或守护进程没起 → 安装 Docker Engine 并启动 dockerd。

体检通过后再继续。

## 2. 第 1 步：依赖准备（版本以锁文件为准）

```bash
make install
# 等价于分别执行：
#   ./scripts/setup-backend.sh     # 建 backend/.venv，按 requirements.lock 精确安装
#   ./scripts/setup-frontend.sh    # npm ci，严格按 package-lock.json 安装
```

要点：

- 两个脚本都**幂等**，反复执行结果一致；后端依赖装进项目内 `backend/.venv`，不污染系统 Python。
- 后端脚本在系统 Python 缺 `ensurepip` 时自动走无 root 引导路径（本指南就是在这样的机器上验证的）。
- 前端用 `npm ci` 而不是 `npm install`：锁文件与 `package.json` 不一致会**直接失败并指出差异**，
  不会悄悄改成新版本。
- 验证装出来的版本：
  ```bash
  backend/.venv/bin/pip freeze        # 应与 backend/requirements.lock 完全一致
  (cd frontend && npm ls --depth=0)   # 应与 package-lock.json 一致
  ```

更新依赖时（不是日常操作）：改 `requirements.txt`/`package.json` 后，重新生成锁文件并提交：

```bash
# 后端
(cd backend && .venv/bin/pip install -r requirements.txt && .venv/bin/pip freeze | \
  grep -v '^packaging==' > requirements.lock)   # packaging 仅为引导环境自带，非业务依赖
# 前端
(cd frontend && npm install)                    # 刷新 package-lock.json 后提交
```

## 3. 第 2 步：启动（启动方式照旧）

本地直跑，和以前完全一样：

```bash
# 后端：监听 http://127.0.0.1:8000
(cd backend && ./run.sh)
# 前端：监听 http://127.0.0.1:5173（dev server 不会自动开浏览器，/api 代理到后端）
(cd frontend && npm run dev)
```

健康检查：

```bash
curl http://127.0.0.1:8000/api/health
# {"ok":true,"app":"特种设备点检运维平台","modules":18}
```

## 4. 第 3 步：样例数据初始化（反复执行不会多出条目）

样例数据的唯一来源是 `backend/app/seed.py` 里的 `SEED_ROWS`（18 个模块，每模块 3 条，共 54 条）。

```bash
make seed-init
# 等价于：(cd backend && .venv/bin/python -m app.seed_cli init)
```

`init` 做了什么、为什么幂等：

1. 先校验基准数据本身：每个模块条数为正、模块内 `id` 唯一；
2. 用**同一份基准数据连续初始化三遍**（新建两个仓库 + 两次 reset），逐模块比对条数，
   任何一次条数增长都判失败——以此保证「反复初始化不会多出条目」；
3. 打印每模块条数、总条数与基准数据指纹：
   `sha256:43366f568d6b566ed8a84de2c7f05fff8bb079630af872ac0267a4f18a1117d7`（54 条）。

后端是内存仓库：**每次 `./run.sh` 启动都重新装载这份基准数据**，所以上一次运行里手工新增/
改动的记录不会带到下次启动；想恢复干净状态，重启后端即可。

针对「运行中服务」的一致性校验（先按第 3 节把后端跑起来）：

```bash
make seed-check   # 或 make verify
# (cd backend && .venv/bin/python -m app.seed_cli check --base-url http://127.0.0.1:8000)
```

它会核对：服务内 18 个模块条数都等于基准（54 条）；压力管道在「全量 / 按关键字 / 按状态」
三种范围下，**列表 `total` 与导出文件的 `total`、`items` 条数三者一致**。

退出码约定（脚本/CI 可直接用）：`0` 通过；`1` 数据条数或指纹不符（数据被污染，重启后端恢复）；
`2` 连不上服务等环境问题（会打印缺的是什么）。

## 5. 第 4 步：容器构建（版本全部固定）

```bash
docker compose up -d --build      # 或 make up
# 后端 http://127.0.0.1:8000，前端 http://127.0.0.1:5173
docker compose ps                 # backend 带 healthcheck，样例自检不过会判不健康
docker compose logs -f backend    # 看启动日志（含启动前样例自检结果）
docker compose down               # 或 make down
```

容器与本地为什么是同一份结果：

- 基础镜像 tag 精确到补丁版本（见第 0 节表格），不是浮动的 `latest`/`3`/`20`；
- 后端镜像 `pip install -r requirements.lock`、前端镜像 `npm ci`，依赖树与本地锁文件完全相同；
- 后端容器启动前先跑 `python -m app.seed_cli check`：样例缺条目/指纹不对会**启动失败并打印原因**，
  不可能带病起来；
- 前端容器通过环境变量 `VITE_PROXY_TARGET=http://backend:8000` 把 `/api` 代理到 compose 里的
  backend 服务（本地直跑时不设这个变量，默认仍是 `http://127.0.0.1:8000`）。

## 6. 第 5 步：核验「本地与容器跑出同一份结果」

用样例数据指纹 + 压力管道导出文件做交叉比对。

指纹（两份环境都应是下面这个值）：

```bash
# 本地
(cd backend && .venv/bin/python -m app.seed_cli check | grep 指纹 || true)
# 容器内
docker compose exec backend python -m app.seed_cli check
# 期望：sha256:43366f568d6b566ed8a84de2c7f05fff8bb079630af872ac0267a4f18a1117d7
```

导出文件逐条比对（JSON 键顺序不影响比较）：

```bash
# 本地服务导出（后端按第 3 节在本机 8000 运行时）
curl -s http://127.0.0.1:8000/api/pressurepipe/export -o /tmp/pp-local.json
# 容器服务导出
curl -s http://127.0.0.1:8000/api/pressurepipe/export -o /tmp/pp-docker.json   # compose 映射同一端口时换个端口或停掉本地后端

python3 - <<'PY'
import json
a = json.load(open('/tmp/pp-local.json'))
b = json.load(open('/tmp/pp-docker.json'))
assert a == b, "本地与容器导出不一致"
print("一致：", a["module"], a["total"], "条")
PY
```

**导出文件条数与列表当前范围一致**（这是固定口径）：

- 后端 `/api/pressurepipe/export` 接收与列表相同的 `keyword`、`status` 参数，返回该范围下的全量条目，
  不分页、不额外裁剪；响应里 `total == len(items)`，且等于同条件列表接口的 `total`。
- 前端「导出压力管道清单」按钮携带与列表页**同一个查询串**，所以列表上看到多少条，
  另存下来的文件就是多少条（全量 3 条；如 `keyword=PRES-0002` 或 `status=在用运行` 各 1 条）。
- 响应带 `Content-Disposition: attachment; filename="pressurepipe.json"`，浏览器直接另存为文件。

## 7. 故障排查（哪一步没过、缺的是什么）

| 失败现象 | 缺的是什么 / 原因 | 处理 |
| --- | --- | ---|
| `python3: command not found` 或版本低于 3.11 | 缺 Python 3.11+ | 安装 Python 3.11；容器方式可直接用镜像，免本机安装 |
| `ensurepip is not available` / 建 venv 失败 | 系统 Python 缺 `python3-venv`，且无 root | 脚本会自动改走 `--without-pip` + get-pip 引导；保持公网可达即可 |
| 下载 `get-pip.py` 失败 | 无公网 | 配代理/内网 PyPI 镜像，或由管理员装 `python3-pip`、`python3-venv` |
| `pip install` 超时 / 找不到版本 | 访问不到 PyPI | 配网络或 `pip install -i <内网镜像>`（镜像构建时在 Dockerfile 同步配置） |
| `npm ci` 报 `EUSAGE` 锁与清单不同步 | `package-lock.json` 与 `package.json` 不一致 | 按第 2 节「更新依赖」重新生成锁文件并提交，不要用 `npm install` 掩盖 |
| `npm ci` 网络失败 | 访问不到 npm registry | 配网络或 `npm config set registry <内网镜像>` |
| 后端起不来，`make seed-check` 退出码 2 | 8000 上没有服务 | 先在 `backend/` 执行 `./run.sh`；容器方式先 `docker compose up -d backend` |
| seed-check 退出码 1、模块条数对不上 | 运行中数据被改/被重复灌数 | 重启后端（内存库启动即恢复基准）；指纹不符则检查 `app/seed.py` 是否被改动 |
| 导出返回 422（`entry_id` 解析失败） | 老代码里 `/export` 被 `/{entry_id}` 路由截获 | 已修复：`/export` 路由声明在 `/{entry_id}` 之前 |
| `docker compose` 命令不存在 | 只有旧版 docker-compose 或没装 compose v2 | 安装 Docker Engine 自带的 compose v2 插件 |
| `docker compose up` 连不上守护进程 | dockerd 未启动 / 当前用户无权限 | 启动 Docker Desktop 或 dockerd，把用户加入 docker 组后重新登录 |
| 容器 backend 一直 unhealthy | 样例自检失败或服务未监听 | `docker compose logs backend` 看具体是哪一行 `[失败]/[缺失]` |
| 前端页面能开但 `/api` 报错 | 容器内代理目标不对 | 确认 compose 里 frontend 的 `VITE_PROXY_TARGET=http://backend:8000` |

## 8. 一键命令速查

```bash
make check-env                      # 环境体检（加 ARGS=--with-docker 连容器一起查）
make install                        # 按锁文件准备前后端依赖（幂等）
make backend                        # 本地起后端 127.0.0.1:8000（照旧）
make frontend                       # 本地起前端 127.0.0.1:5173（照旧）
make seed-init                      # 初始化样例数据 + 幂等自检（54 条，反复执行不增长）
make verify                         # 校验运行中服务：条数 + 压力管道导出/列表一致
make up / make down / make logs     # 容器构建启动 / 停止 / 看日志
```
